## Summary

Chapter 13 is the **synthesis chapter**: it proposes no new technique of its own but ranks every recommendation from chapters 03–12 by impact/effort/risk, orders them into phases 0–3 per hardware tier, draws the dependency DAG, and sets the per-phase latency budget. Per the FutureWork `AGENTS.md` rule that a synthesis/planning task's deliverable is a completion report (not an edit to the chapter doc), this pass produces **an evidence-grounded audit**: for every roadmap row (A1–A8, B1–B7, C1–C7, D1–D4, E1, and the **X "avoid"** row) it records the current implementation status in the codebase, cites the chapter-specific completion report (`REPORT_03`–`REPORT_12`) and the exact source file that proves it, and flags where the shipped state diverges from the roadmap's phase expectation. No code was written in this pass and no chapter document was edited; the only new file is this report.

The headline finding is that **Phase 0 is substantially done and Phase 1 is partially done**, all as _flag-gated, grounding-preserving, off-by-default_ mechanisms whose quantitative effects remain pending the long tests already scripted in `REPORT_03`–`REPORT_12`. Specifically: every Phase-0 code/config row is implemented or already-satisfied (A2, A3, A6, A7, A8 landed; A4, A5 landed; A1 is OS/display config + a GGUF swap, correctly deferred to its long test); the evaluation foundation **E1** is implemented and has already reproduced the chapter's own JEV p95-regression `REJECT` lesson [Measured-here, REPORT_12]; several Phase-1/2 rows exist as safe scaffolding behind flags (**B2** turn-taking logic in the STT service, **B5** reranker off-by-default, **C3** distillation Stage-0, **C6** shopping-demo tool agents, **D2** priority/shedding); and the **X "avoid"** row is respected — evidence compression, HyDE on numeric queries, speech-native answers and T0 KV-chunk reuse are all correctly **not** implemented. The rows that remain genuinely future work are the ones the roadmap itself puts behind a model download, a GPU training run, a serving-engine change, or new hardware (B1, B3, B4, B6, C1, C2, C4, C5, C7, D1, D3, D4, and the student models inside B3/C3). Every "implemented" verdict below is [Measured-here] by a static read of the cited file; every latency/quality _number_ the roadmap attaches to a row stays `[Estimated]`/`[Reported]` until the corresponding report's long tests are run.

## How it was done

The audit is a cross-reference: for each row, _what the roadmap says_ → _which report claims it_ → _which file in the tree proves it today_. The verdict vocabulary is:

- **Implemented** — a flag/function/module that realises the row exists in shipped code (cited file).
- **Already satisfied** — the existing design already met the row; no change was needed/made.
- **Scaffolded (flag-off)** — the mechanism is implemented but ships disabled by default, pending a long test, a download, or a transport/wiring step.
- **Deferred** — not implemented by design, with the roadmap's own reason (download / GPU training / serving-engine change / new hardware / needs human or browser).
- **Correctly not done** — the X "avoid" row; absence is the intended state.

### Divergences from the literal roadmap (flagged per `AGENTS.md` §3)
